## 1. 서비스 개요

- 서비스명: 호텔 전자상거래 플랫폼
- 목적:
    - 사용자: 호텔 객실 예약 및 결제
    - 관리자: 호텔별 정산/예약/결제/재고 관리

## 2. 주요 기능 및 시나리오

### 2.1 조회/검색 시스템

- 지역별 필터
- 날짜/호텔타입/예약사용인원수/예약객실수별 필터

### 2.2 예약 시스템

- 사용자는 해당 호텔의 예약 가능한 날짜/인원/객실수 로 객실 조회
- 원하는 좌석 선택 및 **임시 예약 (10분간 유효)**
- 임시 예약으로 재고 차감된 현황을 다른 유저에게 (실시간) 반영

### 2.3 결제 시스템

- 사용자는 예약된 객실에 대해 계산된 가격으로 결제
- 웹훅으로 서버 상태 갱신,
서버 반영 완료를 **폴링(polling)** 방식으로 확인 → 완료 시 예약확인서 페이지로 이동

### 2.4 정산 시스템

- 지갑(Wallet) 테이블에 정산액 누적, 원장(Ledger) 테이블에 기록 보관
- 정산 완료 시 지갑 테이블에서 잔액 차감 및 원장 테이블 기록
- **오전 3시 스케줄러**로 일괄 정산 처리, 관리자 수동 정산도 가능
- 수동 정산: 날짜별 정산액 부분 처리 가능

### 2.5 재고 관리 시스템

- 예약 확정 건 중 이용 전 객실은 객실 배정 처리
- 관리자 예약취소(→결제취소 연동) 기능
- 예약내역/결제내역/정산내역 조회 기능

## 3. 세부 요구사항

### 3.1 유저 인증 관련 기능

- 기능: 인증을 위한 JWT 토큰 발급
- 포함 정보:
    - Access Token: 메모리(변수) 저장 → XSS로 인한 탈취 방지 (localStorage 미사용)
    - Refresh Token: httpOnly 쿠키 저장 → JS 접근 차단, 요청 시 자동 전송
- 기능: 소셜로그인
- 포함 정보:
  - OAuth2 Client(카카오/구글 등)를 통한 소셜 인증
  - 소셜 로그인 성공 시 기존 회원 조회 → 없으면 자동 회원가입 처리
  - 인증 성공 후 자체 Access/Refresh Token 발급 (JWT 발급 방식과 동일하게 적용)

### 3.2 조회 관련 기능 API

- 기능: 호텔 조회
- 페이징방식 : offset 기반
- 필터 조건:
    - 지역별 필터
    - 날짜 필터 (체크인/체크아웃)
    - 호텔타입 필터
    - 예약사용인원수 필터
    - 예약객실수 필터
- 기능 : 호텔상세 - 객실조회
- 페이징방식 : offset 기반
- 필터 조건: 특정 호텔 + 날짜/인원/객실수

### 3.3 검색 관련 기능 API

- 기능: 호텔 검색
- 페이징방식 : offset 기반
- 검색조건:
    - 호텔명 (우선 매칭)
    - 호텔주소 (차선 매칭)

### 3.4  예약 관련 기능 API

- 기능: 객실 임시 예약
- 조건: 날짜/인원/객실수에 맞는 예약 가능 객실 선택
- 유효 시간: 10분 (임시 해당 재고 차감, 미결제 시 재고 복구)
- 동시성 처리:
    - 임시 예약 시 재고 차감 → (확장:다른 유저에게 잔여 객실 수 실시간 반영)
    - 동시 요청 시 재고 초과 예약 방지 (DB 락)
- 기능: 예약 상태 조회
- 대상 :
    - 유저: 마이페이지에서 조회 →  offset 기반 페이지네이션
    - 관리자: 예약내역 조회 →  offset 기반 페이지네이션
    (필터) : 예약날짜
    (검색) : 예약번호,호텔명,예약자명
- 기능: 예약 취소
- 대상: 사용자취소(임시예약상태) / 관리자취소(결제완료 건, 결제취소 연동)
- 처리: 상태반영,재고복구,결제취소

### 3.5 결제 관련 기능 API

- 기능: 결제 처리
- 대상 : 임시 예약된 객실 (10분 이내)
- 토스 웹훅으로 서버상태(결제상태) 갱신
- 프론트는 폴링방식으로 서버 반영 완료 여부 확인 → 완료시 예약확인서 페이지로 이동
- 정산용 지갑 테이블 정산액 반영 및 원장테이블에 기록 보관
- 기능: 결제취소
- 대상: 관리자 예약취소 연동
- 처리: 결제취소 → 예약 상태취소 → 재고복구 및 상태변경 → 원장테이블 기록보관,지갑테이블 정산액 차감
- 기능: 결제취소
- 대상: 사용자 임시예약취소
- 처리: 마이페이지 → 미결제 예약 취소 → 재고복구 및 상태변경

## 4. 기술적 요구사항

### 4.1 동시성 제어

- 예약: 다수의 사용자가 동시에 같은 객실 예약 시도 시 충돌 방지 (임시 예약 재고 차감 시점)
  - 재고테이블 비관적락 사용
- 정산: 정산 배치(스케줄러)와 관리자 수동 정산이 동시에 동일 대상을 처리하지 않도록 충돌 방지
  - 지갑테이블 비관적락 사용 

### 4.2 멱등성 처리

- 예약/결제/정산 API에 멱등키(Idempotency-Key) 적용 → 네트워크 재시도, 중복 요청으로 인한 중복 처리 방지
- Redis 기반 저장 (도메인+키 조합), processing → completed/failed 상태 전이로 중복 요청 판별
- 도메인별 TTL 분리 적용
    - 예약: processing 1분 / completed 10분(임시예약 유효시간과 일치) / failed 1분
    - 결제: processing 1분 / completed 30~60분 / failed 1분
    - 정산(수동처리): processing 1분 / completed 1일 / failed 1분

### 4.3 성능 및 확장성

- 대규모 트래픽 처리 가능한 아키텍처 설계 (호텔 검색/조회 트래픽 대응)
- 호텔 검색은 페이지네이션, 호텔 조회는 무한스크롤로 화면 성격에 따른 조회 전략 분리
- 검색 성능 향상을 위한 ElasticSearch 활용 고려

### 4.4 보안

- JWT 토큰 생성 및 관리 시 암호화 적용 (AT: 메모리 저장, RT: httpOnly 쿠키 저장)
- RTR(Refresh Token Rotation) 방식으로 토큰 재발급 및 탈취 대응
- 로그아웃/재사용 방지를 위한 AT 블랙리스트 관리 (Redis)
- 사용자 인증 및 권한 관리 철저 (일반 유저/관리자 권한 분리)
- 관리자 관련 API는 권한 별도 검증
- OAuth2 소셜 로그인 시에도 동일한 AT/RT 발급·관리 정책 적용

## 5. 테스트 요구사항

### 5-1. Junit
- 동시성 이슈 테스트 — 동일 객실 동시 예약 시도, 재고 초과 방지 검증
- 멱등성 테스트 — 중복 요청 처리 검증

### 5-2.Postman
- 각 API 단위 테스트 (JUnit 커버리지 대신 Postman으로 API별 검증)


- 결제 시스템의 정확성 검증 테스트 (웹훅 반영, 폴링 확인, 지갑/원장 테이블 연동 정합성)
- 정산 배치 처리 테스트 (스케줄러 일괄 정산, 관리자 수동 정산 부분처리)
- 임시 예약 만료 처리 테스트 (10분 초과 시 재고 복구 검증)
